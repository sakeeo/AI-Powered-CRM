Idempoten per `externalId`. Pesan keluar hanya dari tombol Kirim pengguna (tanpa auto-send/AI). Verifikasi nyata ke gateway belum dilakukan (tanpa kredensial); alur diuji dengan mock `fetch`. | Diputuskan | 2.3 |
| 16  | Bagaimana integrasi Zapier/Make, Google Calendar, dan email disinkronkan? | **Webhook keluar** (Zapier/Make/kustom): endpoint per tenant, event whitelist (`lead.created`, `contact.created`, `deal.created/won/lost`, `quotation.sent`), HMAC-SHA256 `X-CRM-Signature` atas `timestamp.body`, antrean BullMQ retry exponential, unik (endpoint,eventId), URL HTTPS publik (anti-SSRF) — plan 3.7 memperluas event untuk ERP/POS. **Google** per pengguna lewat OAuth milik deployment (`GOOGLE_CLIENT_ID/SECRET`, opsional), token terenkripsi (AAD org+user), refresh otomatis, `invalid_grant` → `revoked`. **Calendar dua arah**: task/call/meeting berjadwal milik pengguna ↔ event (ID deterministik → idempoten; ETag mengenali gema; perubahan Google hanya berlaku bila lebih baru dari CRM; event berpenanda org lain diabaikan); rate limit Google → retry backoff. **Email**: Gmail read-only (subjek + cuplikan untuk email yang melibatkan contact CRM; tak ada pengiriman/penyimpanan isi penuh). IMAP ditunda. Belum diuji ke Google sungguhan (butuh OAuth client); diuji dengan mock `fetch`. | Diputuskan | 2.4 |
| 17  | Bagaimana NL Insights aman dan narasi quotation tidak mengarang angka? | **Insights**: LLM hanya menerjemahkan pertanyaan → *rencana kueri* JSON (whitelist entitas/filter/kelompok/periode, `strict`, divalidasi Zod); eksekusi kode read-only lewat `ctx.db` + `scopeWhere` (tenant & izin pengguna); jawaban disusun kode dari hasil DB — LLM tidak pernah melihat data hasil, tidak menulis SQL, tidak dapat menyatakan organizationId. Pertanyaan tidak disimpan (hanya metadata AI, keputusan #10). **Narasi quotation**: LLM tidak diberi harga & dilarang menyebut nominal; keluaran diperiksa `checkNarrative` (mata uang, %, angka di luar data → peringatan); hanya draf, disimpan lewat form quotation (kolom `narrative`, tampil di PDF). | Diputuskan | 2.5 |
| 18  | Bagaimana report builder, segmen dinamis, dan laporan terjadwal dibuat konsisten & aman? | **Report builder** memakai definisi yang sama dengan NL Insights (rencana kueri whitelist) dan eksekutor read-only yang sama → angka konsisten, selalu mengikuti izin PEMBACA; laporan tersimpan pribadi/organisasi. **Segmen dinamis**: kolom `kind`+`rules` pada `CustomerSegment`; keanggotaan dievaluasi dari aturan (tag, total belanja mata uang default, jumlah deal, recency) setiap kali — tanpa salinan yang bisa basi; tampil di filter Customers, Customer 360, dan laporan "Segmen Pelanggan". Hanya Owner/Admin/Sales Manager mengelola. **Laporan terjadwal**: jadwal diklaim lewat UPDATE bersyarat `nextRunAt` (satu pemenang → tanpa email ganda), penerima harus anggota aktif, dan SETIAP penerima menerima data sesuai izinnya sendiri (`getMemberContext`); butuh izin export; email berupa teks tabel (lampiran ditunda). | Diputuskan | 2.6 |
| 19  | Versi quotation & repeat purchase | Snapshot (header+item, angka string) dicatat tiap penyimpanan yang mengubah isi dan tiap pengiriman ("Dikirim"); perbandingan murni (Decimal), pemulihan hanya Draft dan tercatat sebagai versi baru. Repeat purchase deterministik (tanpa AI): interval rata-rata antar tanggal deal Won → perkiraan; pembeli satu kali dianggap layak ≥90 hari; customer dengan deal terbuka dikecualikan. | Diputuskan | 2.7 |
| 20 | Bagaimana lead scoring dibuat dapat dijelaskan dan aman? | Skor deterministik (bukan LLM) 0–100 dari 8 faktor berbobot tetap yang seluruhnya ditampilkan; dihitung saat dibaca dan TIDAK disimpan/tidak menulis status, owner, maupun tabel apa pun. Konversi historis sumber hanya dipakai bila ≥5 lead per sumber. Lead terkonversi/arsip tidak dinilai; Unqualified dibatasi ≤20. Fitur prediktif lain digerbangi `evaluateQuality` (ambang minimum: ≥20 lead berkontak ≥50%, ≥10 deal tertutup dengan ≥3 Won & ≥3 Lost, riwayat ≥3 bulan). | Diputuskan | 3.1 |
| 21 | Bagaimana prediksi deal dibuat dapat diuji dan tidak otonom? | Model statistik sederhana (bukan LLM): win rate historis per stage (leave-one-out backtest, Brier) + pengali sinyal yang ditampilkan; hanya muncul bila data memadai (≥10 deal tertutup, ≥3 Won & ≥3 Lost). Hanya rekomendasi — tidak ada tombol/aksi yang memindahkan stage atau menulis probabilitas. | Diputuskan | 3.2 |
| 22 | Bagaimana rekomendasi follow-up tetap draf & terukur? | Rekomendasi deterministik dari pola interaksi (kanal/waktu/kadens) + templat draf; tidak mengirim pesan. Menjadi task hanya lewat tombol Terima (server menghitung ulang, tidak menerima isi dari klien); setiap Terima/Tolak dicatat di recommendation_feedback → AI Draft Acceptance Rate = diterima ÷ (diterima+ditolak). | Diputuskan | 3.3 |
| 23 | Bagaimana anomali didefinisikan dan dijaga tanpa aksi otonom? | Tiga detektor murni dengan ambang tetap (VIP activity drop, win rate drop, lead inflow drop); pemindai terjadwal hanya menulis insight_alerts + notifications, idempoten per (subjek, pekan) lewat unique dedupeKey; tidak membuat task/mengubah deal-customer-lead. Penerima: Owner/Admin/Sales Manager + pemilik customer; Sales Rep hanya melihat alert customernya. | Diputuskan | 3.4 |

## Keputusan Teknis (sudah ditetapkan)

| Topik          | Keputusan                                                                                  |
| -------------- | ------------------------------------------------------------------------------------------ |
| Stack          | Next.js (App Router) + TypeScript, modular monolith.                                       |
| ORM            | Prisma 7 dengan driver adapter `@prisma/adapter-pg`; client di `src/generated/prisma`.     |
| Database dev   | PostgreSQL 16 via Docker Compose project ini, host port 5434 (container `crm-postgres`).   |
| Struktur kode  | `src/modules/<modul>/{components,server,schemas,types}`, kode bersama di `src/lib`.        |
| Environment    | Divalidasi Zod di `src/lib/env.ts`; contoh di `.env.example`.                              |
